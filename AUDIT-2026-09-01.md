# Full Security Audit — 2026-09-01

**Scope:** entire repository — static front-end (HTML + ES modules), the
`mca-economy-plugin` and `account linking Plugin Files` Minecraft (Java/Paper)
plugins, and the live Supabase backend (schema, RLS policies, Storage buckets,
Auth config) queried directly via the Supabase project (`hjaywokvgdzhvsoygctc`).
Excluded per scope: `node_modules`/vendor/build output, `.git`, lock files,
CI/CD and infra config (`wrangler.jsonc`, `_headers`, `_redirects` were read
for findings but not modified).

**Stack confirmed by reading the code, not assumed:** a Cloudflare
Pages/Workers static site (no server framework, no `package.json`) backed
entirely by Supabase (Postgres + PostgREST + Supabase Auth incl. native TOTP
MFA + Storage), plus two independent Paper/Spigot Minecraft plugins written
in Java 17 that talk to the same Supabase project over its REST API using a
service-role key. No custom auth, no custom crypto, no server the audit could
find outside Supabase's own managed services.

This is a follow-up to `AUDIT-2026-08-30.md` and several other prior hardening
passes visible in git history (2FA/MFA, CSP, Turnstile, XSS sweep, economy/
congress backend RPC audits). Nearly everything on the standard checklist was
already fixed by that prior work; this pass re-verified all of it against the
current code and the *live* database (not just migration files), and found
one new gap.

## Fixed this session

### 1. `javascript:` URL navigation via decoded `dataset` value — `congress.page.js` — Low/Medium
**Where:** `congress.page.js:463` (render) and `congress.page.js:516` (click handler, pre-fix).
**Risk:** a congress-notification's `link` field was HTML-escaped with `esc()` before being written into a `data-notif-link="..."` attribute — correct for preventing attribute breakout — but the click handler read it back via `a.dataset.notifLink`, which the browser returns **HTML-entity-decoded**, and passed that straight to `window.location.href`. Every other URL sink in this codebase (article/news/archive markdown links, login return-to, nav links) is routed through a `safeUrl()` scheme allow-list; this one wasn't. If a `congress_notifications.link` value were ever `javascript:...`, clicking the notification would execute it in the page's own origin.
**Current exploitability:** no code path in this repo inserts rows into `congress_notifications` (only `select`/no migration for the table exists here), so it's not reachable today through any client-facing feature — but that also means it's un-audited server-side, and it broke the codebase's own stated invariant.
**Fix:** added the same `safeUrl()` helper used in `article.page.js` (allows only `http:`/`https:`/relative) and wrapped the navigation with it; a rejected URL is silently ignored instead of navigated to.
**Re-verified:** `node --check congress.page.js` passes; the only two `window.location.href` assignments in the file/site tree that come from DB data are `login.html`'s already-audited `safeReturnTo()` and this one, now guarded the same way.

## Verified clean (re-checked this session, not just carried over)

- **XSS / output encoding** — spawned an independent, read-only sub-audit of all 9 recently-extracted `*.page.js` files (`article`, `congress`, `economy`, `history`, `index`, `leadership`, `parental-consent`, `server`, `stocks`) created by the `.html`→`.page.js` refactor since the last audit. Confirmed the refactor was a mechanical, byte-faithful extraction: every file still defines/imports its `esc`/`escapeHtml` helper, applies it at every `innerHTML`/`insertAdjacentHTML` interpolation site, and every markdown/link renderer still routes URLs through `safeUrl()`. No double-escaping, no `eval`/`new Function`/`document.write`, no `target="_blank"` missing `rel="noopener"`, no inline scripts reintroduced into any of the 9 `.html` shells. Only the one gap above.
- **Authentication** — Supabase Auth (email+password, Discord/Google OAuth, native TOTP MFA via `auth.mfa.*`). No custom password handling or custom hashing anywhere in the repo — passwords never touch application code. Password minimum length/complexity is enforced client-side (`login.html:853`, 8+ chars, upper+lower) as a UX gate; Supabase Auth is the real enforcement point.
- **Authorization / IDOR** — spot-checked live RLS policies (not just migration text) on `profiles` and on all four Storage buckets directly against the production database. `profiles` is self-or-staff-only for both `SELECT` and `UPDATE`. All four Storage buckets (`archive-files`, `news-images`, `shop-images` public; `message-attachments` private) have `INSERT`/`UPDATE`/`DELETE` policies gated on the matching `user_has_permission(...)` role check, and `message-attachments` reads are additionally scoped to the owning user's folder or staff. Ran Supabase's own security linter (`get_advisors`) against the live project: 64 warnings, all either (a) the standard "a SECURITY DEFINER RPC is executable by `authenticated`" notice on the ~57 intentional website-facing RPCs (each does its own `auth.uid()`/actor-permission check inside — this is the app's designed access-control model, previously audited in the economy/congress migrations), or (b) 3 RPCs executable by `anon`, which I read the source of directly: `user_has_permission` safely returns `false` for a signed-out caller, and `economy_market_summary`/`economy_order_book` intentionally return only public, aggregated market data (price/volume/order-book depth) with no PII — not a leak.
- **Injection (SQL/NoSQL/command)** — no raw SQL string concatenation anywhere; all backend access is through PostgREST (parameterized filters) or `SECURITY DEFINER` RPCs with typed arguments. The two Java plugins' REST clients URL-encode every user-derived value going into a PostgREST filter (`URLEncoder.encode`); the one raw-concatenation site in the economy plugin (`EconomyService.java:250/265`) only concatenates typed `UUID` objects, not attacker-controlled strings.
- **CSRF** — no cookie-based session anywhere (`grep` for `document.cookie`/`Set-Cookie` across the whole repo returned nothing); all Supabase calls carry a bearer token from `localStorage`/memory via the `Authorization` header, which is not ambiently sent by the browser — the standard CSRF vector doesn't apply to this architecture.
- **File upload handling** — uploads go straight to Supabase Storage from the browser, but I confirmed server-side (not just client `accept="image/*"`, which is cosmetic) that all four buckets enforce a real `allowed_mime_types` allow-list and a `file_size_limit` at the Storage layer (checked via direct query against `storage.buckets`), so the client-side `accept` attribute isn't the only control. No path-traversal-relevant filenames reach the constructed object keys (only a lowercased extension and a `Date.now()`/random or `slugify()`d component are used, never the raw filename).
- **Secrets in source** — no real secrets anywhere. The two Java plugins' `config.yml` templates contain only placeholder `service_role_key`/`service-role-key` values (`PUT_YOUR_SUPABASE_SERVICE_ROLE_KEY_HERE` / `PASTE_YOUR_SUPABASE_SERVICE_ROLE_KEY_HERE`) with comments telling the server operator never to commit the real one; `supabase.js`'s embedded key is the public **anon** key, which is meant to be public and is backed by the RLS checked above. `.assetsignore` keeps the plugin sources, `supabase/` migrations, and all `*.md` (including this report) out of the public Cloudflare deployment entirely.
- **Cookie/token config** — no cookies used for auth (see CSRF above), so HttpOnly/Secure/SameSite don't apply. MFA is Supabase's server-managed TOTP (AAL2 flow in `login.html`), not custom.
- **Rate limiting / bot protection** — Cloudflare Turnstile is wired into signup with a real server-side verification path on the `signup-with-email` Edge Function (per its documenting comment in `login.html:277-292`), but the widget currently uses Cloudflare's **"always passes" test site key** (`1x00000000000000000000AA`), which the code itself flags in a comment: *"signup is not bot-protected yet."* This is a known, self-documented placeholder (identical pattern to the `PUT_YOUR_KEY_HERE` secrets above) waiting on the site owner to supply a real Cloudflare Turnstile site key + secret — I can't generate one, and the code explicitly warns that setting only one half breaks signup. **Needs manual attention** (see below).
- **Sensitive data in errors/logs** — all `error.message` values that reach the DOM go through the same `esc`/`escapeHtml` helpers as everything else (confirmed in the sub-audit above); Supabase error messages are already generic (RLS/constraint violations, not stack traces).
- **Encryption in transit** — `_headers` sets `Strict-Transport-Security: max-age=31536000; includeSubDomains` and `upgrade-insecure-requests` in the CSP on every route; all Supabase/API endpoints are `https://`/`wss://`.
- **Encryption at rest** — no application-level "encrypt sensitive fields" need was found: passwords are hashed by Supabase Auth (never touch app code), MFA secrets are held by Supabase Auth's own encrypted storage, and there's no other secret-like column (SSNs, card numbers, etc.) in the schema.
- **Outdated dependencies** — no `package.json`/npm dependency tree exists (pure static site). The one pinned external JS dependency, `@supabase/supabase-js@2.112.4` loaded from `esm.sh`, is pinned to an exact version (not a `@2` tag) specifically to avoid unreviewed supply-chain drift, per the comment in `supabase.js`. `vendor/qrcode.min.js` is vendored locally rather than pulled from a CDN. The Java plugins' only third-party runtime dependency is `gson:2.11.0` (current, shaded into the jar); `paper-api`/`VaultAPI` are `provided`-scope, supplied by the server itself. Per the constraint not to add/upgrade dependencies without asking, no version bumps were made — flagging for the site owner to periodically re-check the esm.sh-pinned Supabase JS version against upstream advisories.

## Findings that still need manual attention (not auto-fixed, with why)

1. **Turnstile is running on the "always passes" test site key** (`login.html:295`) — bot protection on signup is currently inert. **Why not auto-fixed:** requires a real Cloudflare account + Turnstile site key/secret that only the site owner can generate, and the code correctly warns that changing only one side (widget key vs. `TURNSTILE_SECRET_KEY` on the Edge Function) breaks signup entirely. **Action:** create a Turnstile widget at dash.cloudflare.com, then update `data-sitekey` in `login.html` and the `TURNSTILE_SECRET_KEY` secret on the `signup-with-email` Edge Function together.
2. **Leaked-password protection is disabled in Supabase Auth** (confirmed live via `get_advisors`: `auth_leaked_password_protection`). This checks new passwords against HaveIBeenPwned via k-anonymity before accepting them — a real, low-effort hardening step. **Why not auto-fixed:** it's an Auth-service configuration toggle, not something reachable through any of the database/migration tools available to me (not a schema change, but also not exposed as a callable action here). **Action:** Supabase Dashboard → Authentication → Sign In / Providers → Password → enable "Leaked password protection" (or via the Management API). No data loss risk, no code change required.
3. **`economy_companies.treasury_account_id` is a legacy column that duplicates `account_id`** — per `supabase/migrations/README.md`, an unapplied follow-up migration would retire it behind a `CHECK` constraint so it can never drift again. I queried the live table directly: both columns currently match for every existing company (`0` mismatches out of `2` rows), so this is **not an active bug in production today** — it's a robustness/defense-in-depth cleanup, not an exploitable gap. **Why not auto-fixed:** the constraint change is a schema change, which the action boundaries for this audit require asking about first, and it touches money-movement code (`_economy_buy_shares`) where I'd rather the owner review the exact migration before it runs. **Action (optional, low urgency):** apply the retirement migration described in the (locally absent) `20260828_backend_audit_followups.sql` when convenient — I did not find that file in this checkout, only its description in the README.
4. **`congress_roll_call_tally` and `_economy_set_share_price`** were both listed as "not yet applied" fixes in `supabase/migrations/README.md`, but I read their **live** definitions directly from the production database and both already contain the described fix (supermajority thresholds use `>=` and correctly treat 6-of-9 as passing two-thirds; share-price changes are already gated on `economy_company_can(..., 'can_manage_profile')` or `can_manage_economy`). **The README in this checkout is stale relative to production** — no action needed on these two, but worth updating the README so a future audit doesn't re-flag them.
5. **No audit-log trail for congress actions at the DB layer** — noted by the test-suite author in `tests/README.md` as a known, deliberate gap ("doesn't exist yet"). Not a vulnerability by itself, but it means congress vote/certification actions aren't independently auditable the way economy actions are (which do have `_economy_audit`). **Action (optional):** add an audit table + triggers mirroring the economy one, if accountability for congress actions matters to the owner.
6. **`HardcodedAdminListener` in the `MCAVerify` plugin** (`account linking Plugin Files/.../HardcodedAdminListener.java`) grants `mcaverify.admin`/`mcaverify.use` to any UUID listed in `config.yml`'s `hardcoded_admins`, bypassing the server's permission system and the website's own role system entirely — the code's own docstring calls this "effectively a standing backdoor." The shipped config only lists the placeholder all-zero UUID, so it's inert as distributed. **Why not auto-fixed:** this is intentional, documented functionality (an owner/dev fallback for when permissions plugins misbehave), not a bug — removing it would be a functionality change outside this audit's boundaries, not a safe fix. **Recommendation:** keep the list to the minimum necessary real UUIDs, and remove an entry immediately if that person's access should end (it bypasses everything else, including the website's own de-provisioning).
7. **`profiles_update` RLS policy grants column-blind write access.** Anyone holding the `can_manage_minecraft` permission (granted to staff who only need to update `minecraft_*` columns for verification) can, per the policy as written, update *any* column on *any* profile row — including `role`, `email`, etc. — because Postgres RLS policies gate whole rows, not individual columns. **Why not auto-fixed:** this looks like an intentional simplification (grant broader staff access rather than build column-level security), and tightening it (e.g. a trigger restricting which columns `can_manage_minecraft`-only staff may touch) is a behavior change to who-can-do-what that needs the owner's confirmation it wouldn't break an existing admin workflow. **Recommendation:** if `can_manage_minecraft` is meant to be narrower than full profile-admin, add a `BEFORE UPDATE` trigger that rejects changes to non-Minecraft columns from callers who only hold that permission (and not `can_manage_users`/admin/owner).
